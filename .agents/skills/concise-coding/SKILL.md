# 简洁编程

## 目标

满足需求前提下：**diff 尽量小、逻辑尽量直、方法/常量/变量尽量少**，改后行为与改前一致。

## 核心习惯

### 1. 少抽象，调用处直写

- 逻辑只用 **1～2 次**：直接在调用处写，**不**单独抽函数、常量或变量。
- 新增方法仅当同一逻辑 **≥2 处**复用，或明显降低深层嵌套且多方受益。
- 单行读取/格式化（如 `item.id?.toString().orEmpty()`）就地写，不为埋点参数包 `private fun`。
- 使用频次低的函数、常量、变量：**删掉**，在调用处直接使用。

偏好：**方法函数较少、复用性强、常量变量较少**的代码形态。

### 2. 工具类复用

改前先检索项目是否已有等价实现（`LogUtils`、`GotoUtils`、`StringUtils`、各模块 `util/` / `helper/` 等）。

选用顺序：

1. 直接调用已有 API（diff 最小）
2. 在既有工具类上**非破坏性**新增（缺能力且 ≥2 处会用）
3. 无合适归属且跨模块时才新建工具类

扩展工具类时：可新增重载/函数/默认参数；**禁止**改已有函数语义、删改参数、改变返回值含义。

### 3. 老代码：最小改动、改在链路末端

- 只动需求相关行，不顺手改风格、命名、结构。
- 修改尽量落在**调用链终点**（真正消费/展示处），避免上溯大范围改动老业务逻辑。
- 默认不做：全文件 import/方法重排、无关 warning 修复、大范围重构、顺手修历史问题。

### 4. 注释写法

| 形式 | 用途 |
|------|------|
| `/** ... */` | 单纯说明**某个函数**的作用 |
| `//----功能名----//` | 标注**归类后代码块**的大体方向与作用 |

默认不整理整文件注释；仅为本次 touched 的新增/修改处按需补充。不重写、不删除原有注释（除非本次逻辑变更需要）。

### 5. 零回归

- 不改返回值、回调时机、埋点参数、路由键等对外语义。
- 不删「看似冗余」的判空/生命周期/线程切换，除非能证明路径不可达。
- 只删**本次引入**的死代码与未使用 import；不顺手清文件内历史冗余（除非用户要求优化）。
- 修改后清零**本次引入**的 warning；历史 warning 默认不修。

## 工作流

```
检索可复用工具 → 定位最小修改点（倾向调用链末端）→ 就地补逻辑或扩展工具类
→ 清理本次 diff 冗余 → 自检调用链与边界
```

## 自检

- [ ] diff 是否为满足需求的最小集？
- [ ] 1～2 次用的逻辑是否已内联，未多余抽方法/常量/变量？
- [ ] 是否优先复用/扩展既有工具类？
- [ ] 老代码改动是否在链路末端、未扩大影响面？
- [ ] 行为、埋点、边界是否与改前等价？
- [ ] 项目是否还能正常编译？

## 反例 → 正例

**反例**：仅用 1 次的 4 行拼装抽成 `private fun logXxx` 或提到 `companion object` 常量。

**正例**：调用处直接 `FirebaseLogUtils.logEvent(...)` 或 `AppFlyerLogUtils.log(...)`。

**反例**：为单点需求在通用入口加全局处理，牵动整条调用链。

**正例**：在真正消费处（链路末端）内联处理，不动上游公共方法。

**反例**：修一个小 bug 时顺带全文件 KDoc 整理、import 排序、给所有方法补文档。

**正例**：仅为新增/修改的函数写 `/** 作用说明 */`，用 `//----功能----//` 标注 touched 代码块分区。

## 与项目规范

安全、异常、日志仍遵守 `coding-standard-*` 与 HelloGroup 原则；简洁不等于吞异常或删兜底。

优先级：**业务正确 > 不扩大 diff > 复用工具 > 少方法少变量**。
